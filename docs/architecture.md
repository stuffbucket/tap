# Tap architecture

## Product shape

Tap is a standalone recorder, renderer, CLI, and local editor—not a Ghostty plugin. It must own PTYs, synchronize independent panes, preserve both byte directions, evaluate an editable timeline, render offscreen, and stream frames to FFmpeg.

## Current pipeline

```text
keyboard / paste / terminal replies
                  ↓
       Bun PTY + monotonic clock
                  ↕
          child process output
                  ↓
        editable .tap event tracks
                  ↓
      public libghostty-vt 1.0.1
       ├─ cells, styles, cursor, palette
       ├─ Kitty image pixels + placements
       └─ project-clock animation ticks
                  ↓
       Cairo terminal pane surfaces
                  ↓
    split/layout/overlay compositor
       ├─ PNG screenshot
       ├─ raw RGBA → FFmpeg
       └─ local native-frame player
```

The browser folds the same tracks into `ghostty-web` for cells and a pinned Kitty-enabled `libghostty-vt` WASM for image state, placements, and animation. Native-frame mode remains available for exact server compositor output. On macOS, optional `ghostty-screenshot`/`ghostty-video` commands dynamically load the unmodified installed Ghostty.app CoreText/Metal renderer exports and capture its IOSurface before FFmpeg encoding.

## Source boundaries

- `src/capture.ts` owns one Bun PTY and one stable Ghostty terminal per pane. It records exact output, keyboard/paste input, terminal-generated replies, and resizes.
- `src/model.ts` defines the editable versioned project and event vocabulary.
- `native/renderer.c` is a narrow public `libghostty-vt` consumer. It feeds VT bytes, returns terminal replies, advances Kitty animations, reads render state and image storage, and rasterizes one pane.
- `src/native-renderer.ts` owns the framed subprocess protocol to the native renderer.
- `src/render.ts` evaluates pane timelines, composites layouts and overlays, and sends RGBA video frames to FFmpeg.
- `native/vhsparse` directly reuses Charmbracelet VHS's lexer/parser.
- `src/tape.ts` schedules parsed VHS commands against a real Ghostty-backed PTY and records the result.
- `src/server.ts` and `web/` provide playback and non-destructive context-menu edits.

## Recording semantics

Every pane event uses integer microseconds from one monotonic project epoch. Array order resolves equal timestamps within a pane. The lanes are:

- `output`: exact bytes read from the PTY.
- `input`: exact bytes written to the PTY with an origin. Input can be redacted or omitted.
- `resize`: source terminal geometry.
- `scroll`: viewport movement.
- `layout`: presentation/compositing geometry.
- `visibility` and `marker`.

Input is not fed into the terminal emulator during visual playback. The authoritative visual stream is output plus terminal-control events. This prevents a replay from executing commands while still retaining what the person typed.

Terminal replies are generated by the same `libghostty-vt` instance that observes live output, immediately written to the PTY, and recorded as `input` with origin `terminal-reply`. This preserves device-query behavior and both byte directions.

## Kitty graphics

The native backend uses the public image APIs rather than implementing a second Kitty protocol:

1. A bounded libpng callback is installed through `GHOSTTY_SYS_OPT_DECODE_PNG`.
2. Direct RGB, RGBA, grayscale, and PNG transfers are decoded and stored by Ghostty.
3. The render-state image iterator supplies source rectangles, destination sizes, viewport positions, layers, and z indices.
4. Pixel data comes from Ghostty's image storage.
5. Images are sorted and composited in Ghostty's required order: below background, backgrounds, below text, text, above text.
6. `ghostty_kitty_graphics_animation_tick` runs once for every project frame using project milliseconds.

This supports fixed, placeholder, and relative placements represented by the render state, plus animation frame edits and loops implemented by Ghostty.

File and temporary-file transports pass through a bounded streaming normalizer. The original PTY bytes remain authoritative in `output.data`, while `output.playbackData` contains an equivalent direct, chunked packet. Symlinks are resolved before an allow-root check; the pane working directory and system temporary directory are allowed by default, with explicit additional roots in the capture specification. Shared-memory objects are normalized and unlinked through `/dev/shm` on Linux and a bounded POSIX `shm_open` helper on macOS/BSD.

## Frame timing

For constant-frame-rate export:

```text
frame_time_us = start_us + round(frame_index * 1_000_000 / fps)
```

For each frame Tap:

1. applies all pane events through the frame time;
2. advances Kitty animation to that project time;
3. updates Ghostty render state;
4. renders each visible pane;
5. applies layout and overlays;
6. sends one RGBA frame to FFmpeg.

PTY events are never dropped. Interactive preview may coalesce requested native frames to the newest timestamp, preventing a slow client from creating an unbounded queue. Offline export samples every requested frame. The exporter accepts 1–240 fps and has been verified at 120 fps with animated Kitty content.

## Split and resize semantics

A capture specification starts all pane PTYs against the same project clock. Each pane has independent terminal state and source events. Layout events move or resize a complete pane surface. For genuinely live split creation, `tap live` records one tmux-owned PTY and exposes split-right, split-down, focus-next, and close-pane controls through the browser context menu; tmux's exact drawing is part of the recording. The reusable `CaptureSession` API provides Tap-native dynamic `splitPane`, focus/input routing, close, process tracking, atomic layout events, and pre-creation pane invisibility when independent PTYs are required.

Two operations must remain distinct:

- **Terminal resize:** changes rows/columns, reflows Ghostty state, and in a live session sends `SIGWINCH` through the PTY.
- **Layout resize:** scales/crops/moves the recorded pane without changing terminal state.

After capture, layout edits are always deterministic. A new source terminal resize changes how recorded bytes fold but cannot reproduce output the child would have emitted after a live resize. VHS projects can be rerun when semantic resize behavior is required.

## VHS compatibility

The parser sidecar is built against upstream VHS 0.12.1, preserving its grammar, quoting, regexes, settings, and `Source` expansion. Tap implements the terminal-facing command scheduler while replacing VHS's ttyd/xterm.js/Chrome renderer.

Implemented scheduling includes environment and shell setup, requirements, per-character typing, key repeats/delays, Ctrl/Alt/Shift modifiers, sleep, regex waits against line or screen, hide/show, screenshots, output jobs, clipboard copy/paste, and viewport scrolling.

Once live evaluation finishes, the `.tap` event record—not process re-execution—is the deterministic playback source. The upstream compatibility job parses all 109 VHS example tapes and executes a safe representative subset; it also covers leading-decimal durations, default 50ms typing/key timing, late-setting behavior, dimensions errors, frame directories, and text outputs.

## Browser and context controls

The loopback server exposes:

- project JSON read/write;
- Ghostty-WASM cell assets and a direct-Kitty `libghostty-vt` WASM;
- a serialized native-frame endpoint;
- capability discovery.

The player supports native-pixel and WASM-cell views, play/pause, seek, speed, optional input visualization, save/download, markers, visibility, terminal resize, and horizontal/vertical pane layouts. Project writes are validated and atomic.

## Security

- The local editor binds to `127.0.0.1` unless explicitly overridden.
- Playback folds captured bytes but never starts the captured command.
- Input capture defaults to exact recording because it is required for session provenance, but `redact` and `omit` policies are available.
- OSC clipboard and filesystem effects remain inert.
- PNG dimensions and protocol request sizes are bounded.
- Kitty file paths are normalized only within explicit roots; shared memory is read through bounded platform helpers.
- Captured output, labels, titles, and image data are untrusted.

## Large-recording format

The current single JSON file is intentionally inspectable and editable. Long-running sessions should migrate without changing the logical model:

```text
session.tap/
  manifest.json
  project.json
  events/<pane>.tlog
  assets/sha256/<digest>
  checkpoints/<engine-fingerprint>/<pane>/...
```

Event logs should use append-safe independently checksummed chunks and add `(time_ns, global_sequence)`. Raw events remain authoritative. Ghostty snapshots are disposable seek caches because snapshot compatibility is versioned independently from the stable C ABI.
